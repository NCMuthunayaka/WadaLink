WadaLink AI Features Audit Report

**Audit date:** 2026-11-19

**Scope:** Mobile AI experience, backend AI support, ML workspace, and database integration

Executive summary

WadaLink currently contains a working AI feature prototype in the mobile application. Service classification and provider matching are implemented through deterministic mock logic in the mobile code. The screens and user flow are present, but a trained model, backend inference API, real provider data integration, and production AI logging are not yet connected.

**Estimated AI implementation completion: 40%**

The current implementation is suitable for demonstrating the intended product experience, but it should not yet be described as a fully integrated production AI system.

How classification currently works

The mobile mock classifier reads the service description and checks predefined keyword lists. Examples include electrical words such as breaker, plumbing words such as leak, and HVAC words such as AC or thermostat.

It then:

1. Selects the category with the strongest keyword match.

2. Detects hazard words such as fire, spark, gas, flood, or exposed wire.

3. Adjusts urgency when a hazard is detected.

4. Selects a category-specific response template.

5. Returns a generated risk description, possible cause, credentials, duration, cost range, and safety tips.

This is a deterministic rules engine, not an ML model. The request gateway currently points directly to the mock implementation:

const gateway: RequestsGateway = mockRequestsGateway;

How provider matching currently works

The prototype creates a fixed provider list and filters it by category. Each provider receives scores for:

FactorWeight
Rating35%
Proximity25%
Response time15%
Price15%
Experience10%

The final ranking is useful for demonstrating the intended behavior, but it is based on hard-coded provider records and simulated distance values. It is not yet using live provider profiles, availability, location, or historical performance from the backend.

Database readiness

The database has a good foundation for AI integration. Existing structures include:

  • `classification_logs`: model input, output, confidence, category, urgency, status, and model name.
  • `provider_scores`: per-request provider scoring components, total score, rank, and explanation JSON.
  • `service_categories`: category reference data.
  • `service_requests`: user service descriptions and request context.

The missing step is connecting the runtime AI services to these tables. Classification and matching results should be generated by backend services and persisted transactionally for auditability.

Main contradictions and risks

1. The UI presents the feature as AI-powered, while the current implementation is keyword/template-based.

2. The mobile request API always uses the mock gateway, even when the real backend is enabled.

3. Provider matching uses hard-coded provider data rather than database records.

4. Distances and response times are simulated.

5. The ML workspace contains documentation but no integrated training or inference pipeline.

6. AI database tables exist but are not populated by the active request flow.

Recommended implementation path

Phase 1: Backend contracts

  • Add request classification endpoint.
  • Add provider matching endpoint.
  • Define request, classification, and match response DTOs.
  • Return model name, confidence, fallback status, and explanation data.

Phase 2: Model integration

  • Train and version the service-category classifier in the ML workspace.
  • Expose inference through a backend service.
  • Validate confidence thresholds.
  • Use a safe fallback for uncertain or hazardous requests.

Phase 3: Real matching

  • Add provider service-category relationships.
  • Read provider rating, price, response time, availability, and location from the database.
  • Calculate distance from real coordinates.
  • Persist `provider_scores` for each request.

Phase 4: Mobile integration

  • Replace `mockRequestsGateway` with HTTP gateway calls when mock mode is disabled.
  • Display backend classification results.
  • Display backend-ranked providers.
  • Show clear loading, failure, and fallback states.

Phase 5: Verification

  • Add unit tests for classification and ranking.
  • Add API integration tests.
  • Test unsafe descriptions and low-confidence classifications.
  • Verify classification logs and provider scores in Neon.

Final assessment

The AI feature is a functional prototype and a strong UI demonstration, but it is not yet production-integrated. The most important next step is to move classification and provider matching from the mobile mock gateway into backend services, then persist the results in the existing AI database tables.
